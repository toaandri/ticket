======================================================================
00. MISSION, NON-NEGOTIABLE RULES AND DEFINITION OF DONE
======================================================================
Build Ticket, a portfolio-grade, open-source event management and ticketing platform in ONE GitHub monorepo. Deliver a complete responsive React web application, a dedicated React Native mobile application, and a Django backend. Support general-admission inventory AND assigned seating; organizations and staff; event discovery; timed holds; checkout; mock payments and optional Stripe TEST MODE; QR tickets; atomic check-in; refunds; promotions; analytics; email notifications; audit trails; documentation; automated tests; Docker Compose; GitHub Actions. No real payments or live Stripe keys are necessary to run the project. Never claim an unimplemented feature is done.

Repository name: ticket. Product name: Ticket. English source, docs, API and default UI copy. One repository, one canonical backend and database, shared API contract, separate web/mobile clients. No duplicate projects, no microservices, no separate repos. Develop vertically in independently testable phases; complete the core transaction invariants before UI polish. Use current supported compatible stable dependency versions, pin them in lockfiles, document actual versions. Do not blindly assume specific versions or external services. Make reasoned choices in docs/adr. Do not use the product name as evidence of trademark availability; verify separately before commercial deployment.

Definition of done: fresh clone + documented environment setup + docker compose up --build + migrations + deterministic seed yields a functional demo with all four user roles; backend/frontend/mobile tests pass; concurrency and payment replay tests pass against real PostgreSQL; OpenAPI matches implementation; no secrets committed; screenshots and a clear README show actual working features. Mobile must launch in documented emulator/device development workflow and use same backend. External Stripe is OPTIONAL; mock mode works offline except package installation. A mobile emulator is not assumed to run inside Docker.

Scope is a portfolio/demo, not a production payment processor. No actual ticket sales, settlement, tax/legal guarantees, or PCI card handling. Use fake event data and test-mode payments. Never store card numbers, CVV, Stripe secret keys in clients, or raw sensitive webhook payloads in logs. Clearly label simulated revenue and test transactions.

01. PRODUCT PERSONAS AND USER JOURNEYS
======================================================================
Personas: visitor, attendee, organization owner, organization manager, event editor, finance viewer, gate scanner, platform administrator. A user may belong to multiple organizations with distinct roles. Platform superuser is not equivalent to an organizer. Organizer permissions must be scoped to organization and event. Gate scanner can check in only at assigned events, never view finance or attendee exports.

Journeys: visitor discovers/filter events, reads venue/accessibility/terms; attendee registers/verifies email, selects general-admission quantity or exact numbered seats, receives timed hold, checks out, completes mock or Stripe test payment, obtains digital ticket(s), downloads PDF, views order history, receives notification, transfers eligible ticket if enabled; organizer creates organization/venue/layout, invites staff, drafts/publishes event, defines capacity and ticket types, monitors inventory/sales/check-in, issues permitted refunds/cancellations; gate staff scans online QR, sees unambiguous accepted/duplicate/invalid/revoked response and audit trail; administrator handles moderation and incident review. Define error, empty, loading, accessibility and expired-session paths for each journey.

Out of scope v1: real bank settlement, cash payouts, tax compliance, offline check-in synchronization, dynamic resale marketplace, seat-map CAD editor, multi-currency checkout in one order, cryptocurrency, AI recommendations, arbitrary untrusted webhooks. Optional future enhancements require ADRs and tests.

02. TECHNOLOGY AND ARCHITECTURE
======================================================================
Backend: Python, Django, Django REST Framework, PostgreSQL, django-filter, drf-spectacular, Celery, Redis, Django Channels/ASGI for realtime, pytest/pytest-django, factory_boy, coverage, Ruff, type checking where practical. Explicit application service layer for transactions; thin DRF views/serializers; domain models with DB constraints; selectors for complex reads. Use Django built-in auth with custom user model defined before first migration; choose robust session/CSRF or short-lived JWT + refresh strategy, document rationale and mobile secure storage. Prefer session+CSRF for browser and access/refresh token flow for mobile if implementing dual auth; do not place long-lived tokens in localStorage. Throttle login and sensitive endpoints.

Web: React + TypeScript + Vite, React Router, TanStack Query, React Hook Form + Zod, Tailwind CSS and accessible component library, typed generated API client from OpenAPI; responsive participant pages and separate organizer/scanner/admin routes. Mobile: React Native with Expo + TypeScript (document SDK and compatible libraries), Expo Router, secure token storage, camera QR scanning with permissions, attendee wallet and organizer scanner workflows, shared generated API types in packages/api-client. Use native device camera only after permissions; offer manual token entry in development. Avoid embedding secrets in Expo public variables.

Infrastructure: Docker Compose services postgres, redis, backend ASGI, celery worker, celery beat, web, optional local email sink (Mailpit or equivalent). Healthchecks, restart policies, named volumes, environment examples, no public production DB/Redis ports. ASGI supports HTTP and WebSockets. Use transactional outbox for post-commit critical messages or at minimum transaction.on_commit plus durable retry records; document delivery semantics. PostgreSQL is sole source of truth for inventory and ticket validity; Redis is NOT inventory authority. Store media in local dev volume; abstract storage for future S3-compatible object storage. Structured logs, request/correlation IDs, no PII/tokens in logs, metrics endpoints restricted.

Architecture: browser/mobile -> versioned DRF API -> application services -> PostgreSQL; Celery/beat -> same services/DB for expiration, email and reporting; Channels -> availability broadcasts AFTER commits, clients refetch authoritative availability. PaymentProvider interface: MockPaymentProvider default; StripeTestPaymentProvider optional backend-only. All external callbacks enter a verified webhook endpoint and durable event inbox.

04. DETAILED CONCEPTUAL DATA MODEL (MCD / ERD)
======================================================================
Implement migrations, textual ERD and Mermaid ERD in docs/database; list cardinalities, ownership, lifecycle, deletion policy and indexes. Suggested entities/fields below; refine without weakening invariants.

User(id UUID PK, email CITEXT or normalized unique email, password hash, display_name, email_verified_at, is_active, created_at, updated_at). Organization(id, slug UNIQUE, name, status, owner_id FK User, created_at). Membership(id, organization_id FK, user_id FK, role enum OWNER/MANAGER/EDITOR/FINANCE/SCANNER, status, invited_by, joined_at, UNIQUE(org,user)); Invitation(id, organization_id, email, role, token_hash UNIQUE, expires_at, accepted_at). EventStaffAssignment(id, event_id, membership_id, permission, UNIQUE(event,membership,permission)). AuditLog(id, actor_id nullable, organization_id nullable, event_id nullable, action, entity_type, entity_id, metadata_redacted JSONB, ip_hash, created_at; append-only application semantics).

Venue(id, organization_id nullable, name, address text, city, country_code, timezone IANA, accessibility_info, status). VenueSection(id, venue_id, code, name, capacity nullable, UNIQUE(venue,code)). Seat(id, section_id, row_label, seat_number, label, accessible boolean, status, UNIQUE(section,row_label,seat_number)); venue layout version must be immutable once tickets exist for an event. Event(id, organization_id, venue_id nullable, slug, title, description, category, banner, start_at UTC, end_at UTC, event_timezone, status DRAFT/PUBLISHED/CANCELLED/COMPLETED, seating_mode GENERAL/ASSIGNED/MIXED, sales_start_at, sales_end_at, age_policy, cancellation_policy, published_at, version, created_at, UNIQUE(organization,slug)); EventSection(id,event_id,venue_section_id, layout_version, capacity, UNIQUE(event,venue_section)); EventSeat(id,event_id,seat_id, event_section_id, availability_status optional derived, UNIQUE(event,seat)); do not rely on mutable status alone to enforce exclusivity. EventTicketType(id,event_id,section_id nullable, name, code, kind GENERAL/ASSIGNED, price_minor, currency, quota, per_order_limit, sale_start_at, sale_end_at, status, UNIQUE(event,code)); SeatTicketType mapping where multiple types could apply to seats, with unambiguous allocation rules. InventoryBucket(id,event_id,ticket_type_id, capacity, held_count, sold_count, version, UNIQUE(event,ticket_type)); CHECK held_count>=0, sold_count>=0, held_count+sold_count<=capacity; adjust in locked transaction only.

Reservation(id, user_id, event_id, status ACTIVE/CONSUMED/EXPIRED/CANCELLED, expires_at, idempotency_key scoped to actor+operation, created_at, updated_at); ReservationItem(id,reservation_id,ticket_type_id, event_seat_id nullable, quantity, unit_price_minor snapshot, currency, status ACTIVE/CONSUMED/RELEASED, CHECK quantity>0, CHECK assigned seat quantity=1). To enforce assigned seat exclusivity, maintain SeatClaim(id,event_id,event_seat_id, reservation_item_id nullable, order_item_id nullable, state HELD/SOLD, expires_at nullable, UNIQUE(event,event_seat_id) for currently held/sold claim; use ONE current claim row per event-seat and release/delete under lock; preserve historical claims in append-only SeatClaimHistory. Alternatively partial UNIQUE(event,seat) WHERE state IN ('HELD','SOLD') plus transactional expiration, but ensure stale held rows are transitioned before acquisition. Never use a partial index predicate depending on NOW(). For GA, locked InventoryBucket counters plus reservation item lifecycle and reconciliation are authoritative.

Order(id, user_id, event_id, reservation_id UNIQUE nullable, public_reference UNIQUE, status PENDING/PAYMENT_PROCESSING/PAID/FAILED/EXPIRED/CANCELLED/PARTIALLY_REFUNDED/REFUNDED, subtotal_minor, discount_minor, fees_minor, tax_minor, total_minor, currency, expires_at, created_at, paid_at, version); OrderItem(id,order_id,ticket_type_id,event_seat_id nullable, quantity, unit_price_minor, discount_minor, total_minor, attendee_name optional, UNIQUE(order,event_seat_id) where seat not null). PaymentAttempt(id,order_id,provider MOCK/STRIPE_TEST, provider_payment_id nullable UNIQUE scoped provider, idempotency_key, amount_minor, currency, status CREATED/PENDING/SUCCEEDED/FAILED/CANCELLED/REFUNDED, created_at, updated_at, provider_metadata_redacted); PaymentEventInbox(id,provider,event_id, payload_digest, received_at, processed_at, processing_status, UNIQUE(provider,event_id)); Refund(id,order_id,payment_attempt_id,amount_minor,currency,reason,status,provider_ref nullable,requested_by,created_at,completed_at,idempotency_key). Refund allocation to order items/tickets must be explicit.

Ticket(id,order_item_id,event_id,holder_user_id nullable, ticket_type_id,event_seat_id nullable, token_hash UNIQUE, public_code UNIQUE, status VALID/USED/REVOKED/REFUNDED/TRANSFERRED, issued_at, used_at, revoked_at, version); generate ONE Ticket per admission even if OrderItem.quantity>1. TicketTransfer(id,ticket_id,from_user,to_email,token_hash,expires_at,status,created_at); CheckIn(id,ticket_id, event_id, scanned_by, scanned_at, device_id nullable, result ACCEPTED/DUPLICATE/INVALID/REVOKED/WRONG_EVENT, UNIQUE(ticket_id) WHERE result='ACCEPTED'); rejected attempts may be logged separately. Promotion(id,organization_id,event_id nullable,code,kind PERCENT/FIXED,amount,usage_limit,per_user_limit,start_at,end_at,active); PromotionRedemption(id,promotion_id,order_id,user_id,amount_minor, UNIQUE(promotion_id,order_id)). Notification(id,user_id,kind,template,data_redacted,status,attempts,next_attempt_at,created_at); OutboxEvent(id,event_type,aggregate_id,payload_redacted,created_at,published_at,attempts); EventMetricSnapshot(id,event_id,bucket_start,metric_name,value, UNIQUE(event,bucket_start,metric_name)).

Cardinalities: User 1:N Membership and Organization 1:N Membership (N:M users/orgs); Organization 1:N Event; Venue 1:N Section; Section 1:N Seat; Event 1:N TicketType/EventSeat/Reservation/Order; Reservation 1:N ReservationItem and at most 1 Order; Order 1:N OrderItem/PaymentAttempt/Refund; OrderItem 1:N Ticket (GA) or 1:1 Ticket (assigned); Ticket 0:1 accepted CheckIn; Event 1:N staff assignments. Explicitly prohibit hard delete for paid orders, tickets, payment events and audit logs; use status transitions and retention policy. Define ON DELETE PROTECT/RESTRICT for financial records, CASCADE only for safe ephemeral drafts, and soft delete where appropriate.

05. POSTGRESQL INVARIANTS, INDEXES AND MIGRATIONS
======================================================================
Enforce uniqueness for org slug, normalized email, membership, venue seat coordinates, event-seat, ticket token hash, provider event ID, provider payment ID, order public reference, reservation/order idempotency scope. Add CHECK for nonnegative money, quantity>0, start_at<end_at, sales_start_at<sales_end_at, valid currency code, bounded percentage, held+sold<=capacity, total=subtotal-discount+fees+tax where feasible. Cross-row constraints require locked services, not naive CHECKs. Use partial unique indexes for active seat claims and accepted check-ins; verify PostgreSQL syntax and migration behavior. Add indexes on (event,status,start_at), (reservation,status,expires_at), (order,user,created_at), (ticket,event,status), (payment provider,provider ID), outbox status, inbox processed_at, membership(org,user), search/filter columns. Use PostgreSQL case-insensitive unique email via normalized stored value or appropriate collation/index. Use migrations only, no runtime schema creation; migration rollback strategy and data migrations documented. Avoid SQLite for inventory/concurrency testing; SQLite select_for_update behavior is not representative.

Every state transition uses a named service and row locks in consistent order (event/bucket -> reservation/seat claims -> order -> payment/ticket as appropriate), with bounded transaction time and retry on serialization/deadlock where justified. DB transaction never spans a remote Stripe request or 10-minute hold. Use transaction.on_commit for notifications/broadcasts; durable outbox for must-deliver side effects. Write reconciliation command to recompute inventory from authoritative claims/orders and flag mismatches without silent destructive correction. All inventory mutation paths, including admin, refunds, event cancellation and expiration, use same services.

06. RESERVATION ENGINE: PRECISE STATE MACHINES
======================================================================
Hold TTL configurable default 10 minutes. Availability API is advisory; final decision always inside DB transaction. Client must display server expires_at, not trust client clock. Idempotency-Key required on create reservation, create order, payment initiation, refund and check-in; persist request fingerprint and response mapping scoped to actor/endpoint; same key+same payload returns same result; same key+different payload returns 409. Constrain max quantities, per-user caps and rate limits.

ASSIGNED: in atomic transaction, validate published event, sales window, type/seat compatibility, limits; acquire deterministic ordered locks for requested event-seat or claim rows (handle absent-row race with unique index + IntegrityError retry); release expired claims transactionally before acquiring; insert exclusive active claim; create ReservationItem; commit; broadcast only after commit. Competing request gets sold/held conflict (409) or a retryable response; never double hold. For seat availability, do not depend solely on a boolean seat.status. Expiration worker selects ACTIVE reservations with expires_at<=DB now using select_for_update(skip_locked=True) in batches, marks EXPIRED, releases seat claims/GA held counters exactly once. Checkout must revalidate expiry under same locks; expired hold cannot be resurrected by delayed payment.

GENERAL ADMISSION: lock InventoryBucket row with select_for_update, verify capacity-held-sold>=requested quantity, increment held_count, create reservation and items; on expiration decrement held once; on successful purchase decrement held and increment sold atomically; no negative counts. Maintain reconciliation and audit records. Mixed events may have both types but one order is single event/currency; enforce per-order and per-type limits.

Checkout: lock reservation, validate ownership/ACTIVE/unexpired and item snapshot, create one order per reservation (UNIQUE reservation_id), immutable pricing breakdown, apply promotion atomically with redemption limits, transition reservation to CONSUMED only at the defined point; clarify that inventory remains reserved during payment pending until a documented deadline. Suggested design: keep claims HELD while order PENDING, with payment deadline <= reservation expiry or explicit short checkout extension recorded transactionally. If payment succeeds before deadline, lock order/claim/bucket and atomically mark SOLD, order PAID, emit tickets; if payment succeeds after expiration or after cancellation, DO NOT issue tickets; record exception and initiate test refund/compensation. Define recovery for pending webhook, partial failures and duplicate callbacks. If order expires, release holds once and mark order EXPIRED. No orphan active claims. State transition matrix and sequence diagrams required in docs.

Cancellation/refund: permission and event policy check; refund amount <= remaining captured test amount; idempotent refund attempts; revoke affected tickets, update sold inventory only if event resale policy allows, release seat claims transactionally, adjust counters once, append audit. Used tickets generally not refundable by default unless admin override with recorded reason. Event cancellation bulk workflow is batched, resumable and audited.

08. QR TICKETS AND CHECK-IN
======================================================================
Generate random cryptographically secure opaque ticket secret (>=128 bits entropy); store hash, not raw secret, where possible; QR contains HTTPS validation URL or signed opaque payload, never PII or predictable DB ID. PDF and mobile wallet render code, event, date, venue, seat/type and terms; use secure download authorization and short-lived signed download URLs where applicable. Ticket transfer rotates/revokes old secret and invalidates old QR, preserving audit. QR scanning requires online connectivity in v1; display explicit offline-unavailable status, do not queue unverified admissions. Scanner is assigned to event and authenticates via scoped role. Atomic check-in locks Ticket, verifies event, VALID, event check-in window and no accepted scan, transitions to USED and writes accepted CheckIn once; duplicate returns clear conflict, concurrent scans yield exactly one ACCEPTED. Log invalid attempts with rate limits and redaction. Prevent enumeration; no public endpoint that reveals holder PII for arbitrary QR token.
